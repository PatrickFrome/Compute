# Local Vault Compatibility

The current Native Supervisor code does not call `vault`. Historical duel wake functions read `vault.decrypted_secrets` to sign a legacy `pg_net` wake request. The source database nevertheless includes the `supabase_vault` extension, whose encrypted table contents belong in a full backup.

`local-vault-compat.sql` implements the official version 0.3.1 table, view and function interface on portable PostgreSQL 17 using pgcrypto AES256 PGP encryption. This is a replacement provider; it does not reproduce Supabase's custom AEAD ciphertext or Supabase's inaccessible root key. Source ciphertext remains unmodified in the original backup. A nonempty source vault requires a separate private export of decrypted values and explicit re-encryption; restored original ciphertext fails closed until that transfer succeeds.

Apply the SQL as the trusted local administrator after `pgcrypto` is installed in `extensions`. Its `vault.secrets` table must exist before restoring the extension configuration table data. A phased restore may restore the source `vault` schema first, apply this compatibility SQL, and restore the remaining objects excluding only the unavailable `supabase_vault` extension creation/comment items. Keep the original dump unchanged and record the excluded item IDs and provider difference in the restore receipt.

`initializeLocalVaultKey({dataDirectory})` from `local-vault-key.mjs` creates `client-vault.key` within PostgreSQL's private data directory. It requires an existing PostgreSQL 17 directory outside the repository, rejects symlinks and hardlinks, preserves an existing valid key, and restricts permissions to the local Windows account plus SYSTEM, or mode 0600 on Unix. The key is random 256-bit hex text. It is never passed in SQL, a database setting or a log. A tightly scoped administrator-owned function reads this fixed file through PostgreSQL's privileged file reader. The key file must accompany a private local backup; a database dump alone cannot decrypt local vault values.

Only trusted `service_role` receives the decrypt view and create/update interface. Anonymous/authenticated roles and PUBLIC receive no vault access. The raw key reader is not granted to service_role. Ciphertext contains an encrypted envelope binding secret bytes to the row ID, context and nonce. Changing those values fails decryption rather than relocating a secret. Encryption is randomized, not deterministic. Plaintext is encrypted before insertion into the table.

Do not expose a vault or SQL endpoint through the HTTP adapter. The local DB administrator can read the key and plaintext, as in any client-owned database. Ciphertext, plaintext exports and key files stay outside GitHub and the repository. Secrets can be re-encrypted while preserving ID/name/description/timestamps, but encrypted source-byte equality must not be claimed for such a transfer.

`local-vault.integration.test.mjs` checks encryption/decryption/update, row/nonce binding, denied public role access, service_role view access and key privacy in database function definitions. Its unique fixture is deleted after the test. It requires only the restored local administrator URL in `LOCAL_STATE_TEST_ADMIN_DATABASE_URL`.
