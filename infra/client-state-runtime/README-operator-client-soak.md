# W34 — METAENGINE Client Operator 100-task soak (source candidate)

This is a deterministic **read-only Client Operator Gateway** workload, **not** the separate DevFleet coding-conveyor 100-task soak. It neither enqueues 100 tasks nor starts a new Scheduler/Supervisor; all 100 rows already exist in a disposable own-PostgreSQL fixture. No production PostgreSQL instance, Browser, Guardian, DevFleet, Supabase, cloud endpoint, installed application or live task is modified.

- Fixed task IDs `task-0001`…`task-0100`; exactly one canonical staged run/Owner epoch and 100 contiguous proof-digest-bearing events. A single existing `/operator/v1/context` identity is checked, then `/run_status`, 100 `/inspect` calls at **max 4 concurrent GETs**, and four cursor-paginated `/events` GETs (32/32/32/4). The core rejects mismatched identity/epoch, false readback, incomplete task, stale/missing projection, cursor gap/duplicate, incorrect watermark, unexpected status and missing proof. **106 GETs**, zero mutation routes.
- Per-request measured latency (p50/p95/p99/max) and sampled `heapUsed` growth. Default gates: p95 <= 5000 ms, peak heap growth <= 64 MiB. Thresholds are deliberately broad CI regression tripwires, **not** proof of production SLOs; timings are measured nondeterministically even though workload inputs/order are deterministic. The report contains no credentials or task text.
- Hermetic falsification suite: `node --test operator-client-100-task-soak.test.mjs`. Integration: `node --test operator-client-100-task-soak.pg17.integration.test.mjs` only with **explicit** disposable fixture URL `postgres://postgres:<fixture-password>@127.0.0.1:5432/checkpoint_fixture`. The integration test verifies PostgreSQL 17 and its DB name, uses `pg_temp.w34_soak_rows` inside a pinned transaction with `ON COMMIT DROP` and static parameterized SELECTs for readbacks. No persistent DDL/DML, no production DB fallback.
- A dedicated SHA-pinned workflow runs hermetic tests on Ubuntu/Windows and disposable own PG17 tests on Ubuntu. When fixture environment is absent the PG test skips: that is **UNKNOWN**, never evidence of a physical PG pass. The Gateway is authenticated and loopback-only, with bounded payload and request timeouts, using the existing W3 source and no new listener outside the test process.

**Qualification:** source/staging benchmark only. The staged Owner/readback callbacks prove interaction with the temporary fixture, **not** authentic Windows/native process identity, installed Client health, operational performance, workload admission, or a 100-task production execution.
