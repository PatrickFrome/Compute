**Независимая записка по приватной ветке RunCore — 2026-11-03**

Проверен итоговый staged diff из 9 файлов поверх `37786581dfdc74de7371aa6a553a9c204793d4f9`. Это реализованный исходный компонент с сохранённым **HOLD**, а не работающий genuine issuer. В этой заключительной проверке тесты повторно не запускались; файлы репозитория не изменялись.

В существующую единственную C#-сборку `runner` добавлена приватная `RecoveryDirectoryScope` внутри первоначального владельца Job. Исходник предусматривает удержание исходных объектов каталогов, предков и прямых дочерних anchors, object-relative `ReOpenFile`, проверки native identity/reparse/case state, фиксированного backup leaf/parent и непересечения backup с PGDATA. Для наблюдённого остановленного CREATE-события он сохраняет исходный process object, переносит все удерживаемые opens в конкретного worker и сравнивает копии обратно до Resume/Continue. Есть одноразовые слоты, поколения, точный process birth, запрет повторного PID и предел 256 worker rows. Debug-вызовы остаются на исходном OS thread. Приватная C#-ветка не передаёт Job внешнему переживающему процессу.

Освобождение в исходнике требует продолженного EXIT-события, сигнализированного сохранённого process handle, проверки того же process object/birth, пустого Job и завершения исходных I/O tasks, включая control reader. Запрос terminate, callback или отмена сами по себе не означают завершения. При UNKNOWN владелец не закрывает свои исходные opens и сохраняет карантин; это не гарантирует сохранность удалённых копий у worker.

Genuine issuer отсутствует: публичные `Run`/`RunPolicy` по-прежнему передают `null`, а вызовов конструкторов `OriginalRecoveryBundle` и `OriginalRecoveryBirthCoverage` нет. Не реализован исходный authenticated native handoff от service/controller к этому владельцу с подлинной namespace/Owner/Host/own-PG provenance, полной гарантией перехвата рождения каждого effectful потомка и непрерывного удержания его копий. Debug CREATE даёт лишь локальный барьер наблюдённого события: nested debug chains и broker-created процессы не покрываются автоматически. Worker способен закрыть или переиспользовать собственные handles после успешного readback. Проверки `active==0` и `total==workers.Count` — дополнительные условия cleanup; они не доказывают, что ненаблюдённый потомок никогда не выполнялся, и не дают допуска. Также отсутствуют подлинный cancellable control-reader join и квалификация loader handling. Обе реальные JS-точки отказа и selector HOLD сохранены; нового wire permit, ключа, helper binary или trust root нет.

Критическое исправление share-mask внесено в `C++ capture и exclusive creation` и C# reopen: теперь обязателен бит `FILE_READ_DATA` / `FILE_LIST_DIRECTORY` (`0x00120081` в C#) при `FILE_SHARE_READ`. Прежний metadata-only mask не участвовал в требуемых share checks. Модель исправлена: симметричные проверки применяются только к двум участвующим opens после раскрытия generic access, согласно [MS-FSA 2.1.5.1.2.2](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/8c0e3f4f-0729-49f4-a14d-7f7add593819). Отказ в data/list access остаётся отказом, без metadata-only или path fallback. Это исправление исходной механики, не результат Windows qualification.

Четыре синтетических counterexamples намеренно подтверждены как границы неподдерживаемых схем:

1. Внешний переживающий дубликат Job подавляет kill-on-last-close при смерти исходного владельца.
2. Членство потомка в Job без его directory copies оставляет crash gap.
3. Worker закрывает копии после readback; затем смерть владельца оставляет namespace gap при ещё незавершённой работе. Kill request не равен physical join.
4. Старый metadata-only open с `FILE_SHARE_READ` не блокирует DELETE access и rename каталога/anchor.
