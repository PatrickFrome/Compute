## Что уже есть в METAENGINE

В `infra/client-state-runtime/native-coding-agent-host-tools.mjs` реализованы `project_overview`, `project_history_page`, `agent_send_message`, `project_propose_children` и отдельный `READ_INTENT`. Вызовы привязаны к project/run/task/lease, generation, текущему Host и worker. Запись проходит в serializable transaction с `synchronous_commit=on`. Повторное чтение intent не даёт полномочий исполнить эффект.

`native-coding-agent-project-tools.integration.test.mjs` содержит проверки durable message receipt и истории; `native-coding-project-continuation.integration.test.mjs` — цепочки Writer/CRITIC/checkpoint. Комментарии прямо помечают часть данных как SQL fixtures. Эти тесты не являются доказательством физического запуска установленного клиента.

В `native-coding-host-seed-service.mjs` обнаружена архитектурная граница масштаба: перед seed проверяется весь `p.agents`, с параллелизмом максимум четыре и единым окном 25 секунд. Чем больше roster, тем меньше шансов уложиться. Разрешённый большой каталог агентов не равен возможности одновременно проверить и запустить его целиком.

## Пять целевых изменений

1. **Сделать admission наблюдаемой стадией.** Сохранять по `request_id` фазу, длительность и ограниченный код отказа до dispatch. UI должен отличать «проверяется», «допущено», «выполняется», «результат неизвестен» и «отклонено до запуска». Не превращать тайм-аут IPC в разрешение повторной отправки. Сначала можно добавить read-only диагностику, не меняя семантику строгого rejection receipt.

2. **Отделить большой каталог от ограниченного пула исполнения.** В долгосрочном контракте admission проекта фиксирует каталог, а свежая физическая проверка относится к выбранным для конкретного claim исполнителям. Не допущенные slots остаются ожидающими. Ближайшая оптимизация для двух ролей — совместить только одновременно выполняющиеся одинаковые read-only проверки Host/PG внутри одного scope; не кешировать завершённые решения и не переносить их через incarnation/transaction. Полный переход требует тестов контрактов и SQL; одного повышения timeout недостаточно.

3. **Доказать доставку, а затем использование сообщения.** Уже существующий durable message receipt означает запись. Для UI и приёмочного теста отдельно нужны адресат/generation, history sequence, факт чтения и ссылка на использованный результат. Peer discovery должен выдавать актуальную страницу roster и текущие задачи, а не загружать каждому всю историю каждого агента. Это уменьшит контекст и позволит отличать «общаются» от «в базе есть сообщения».

4. **Сохранить единый путь результата и продолжения.** Writer → независимый CRITIC → проверенный Git/checkpoint → следующая runnable задача. Propose children создаёт долговечные задания; scheduler выделяет ограниченные слоты по ресурсам и защищает worktree от двух писателей. На restart восстанавливаются идентичности, checkpoint и pending задачи. Неопределённые физические эффекты требуют readback, а не replay. Отдельный unbounded orchestrator рядом с существующими механизмами не нужен.

5. **Собрать рабочую панель вокруг этой цепочки.** Для каждой задачи показывать родителя, исполнителя, состояние lease, текущую фазу, последнее durable событие, результат CRITIC, checkpoint и причину ожидания. Для сообщений — записано/прочитано отдельно. Кнопка Run должна отображать один request и его последующую судьбу. UI берёт состояние из подтверждённых receipts и событий, а не считает число вкладок доказательством активных агентов.

## Ближайшее доказательство

Принять одну небольшую задачу в установленном клиенте. Получить реальную правку Writer, независимый CRITIC, адресное сообщение с проверенным чтением, checkpoint и автоматически запущенную дочернюю задачу. Затем выполнить контролируемый restart между завершёнными шагами и подтвердить продолжение с того же checkpoint без повторных эффектов. Только после этого расширять pool и длительность прогона.

«Неограниченное множество» технически означает отсутствие фиксированного потолка долговременного каталога и числа последовательных задач при ограниченном физическом параллелизме. Конечный тест доказывает конкретную длительность и число циклов; буквальную бесконечность конечным прогоном доказать невозможно.
