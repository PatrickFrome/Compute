# Управление клиентом и ПК из чата — исходный кандидат

Дата: 2026-10-08. Ветка: `work/client-github-chat-control-v1`.
База: PR #1167, `bdab03db1a5092f28a20138a194cb0f90745f2f1`.
Новая идентичность пакета: `0.7.0-dev.37781000012.1`.

Клиент получает канал доставки команд через отдельную приватную GitHub Issue. Чат и его агенты могут запрашивать состояние клиента, доступные действия, окна, UI Automation и снимки экрана, отправлять команды браузеру и Windows executor, ставить существующие Client V1 цели и читать результат из PostgreSQL. Первоначальная привязка находится в Settings → Runtime → «Управление из чата»; токен вводится в отдельном локальном окне. После привязки нет подтверждения каждого действия.

Это изменение исходного кода. Оно не доказывает установленное подключение к ПК владельца, готовность его восстановленного PostgreSQL, успешную Windows-квалификацию или выпуск установщика. Привилегированные и защищённые рабочие столы Windows не становятся доступными через эту привязку. Предшествующий stdio MCP остаётся отдельным механизмом; новый канал не выдаётся за подключённый MCP-туннель.

## Подключение

1. Установленный клиент должен уже использовать допущенный локальный PostgreSQL/API и зарегистрированное устройство с действующим ADMIN / CONTROL_PLANE. Отсутствующий или неподтверждённый провайдер не переключается на облако.
2. В интерфейсе выбирается существующий приватный репозиторий с включёнными Issues. В локальную форму вводится GitHub token с Metadata read, Issues read/write и Contents read/write. Подключённому к чату GitHub-приложению также нужен доступ к этому репозиторию. Публичный `PatrickFrome/Compute` содержит только исходники.
3. Клиент проверяет числовой ID пользователя, ID и приватность репозитория, создаёт приватную Issue и сохраняет точную привязку устройства, Issue и relay UUID. Issue сразу содержит протокол, адресата и пример запроса для агента. Парольный токен не попадает в Issue, состояние Browser, командную строку или журналы.
4. Токен хранится в зашифрованном `safeStorage` файле профиля. Незашифрованный backend `basic_text`, символьные ссылки, hardlink и доступные другим пользователям POSIX-файлы отвергаются. Окно привязки имеет sandbox, context isolation, отключённый Node и запрет сетевых запросов renderer.

Команда поступает от GitHub User с разрешённым числовым ID. Имя пользователя, текст страницы или инструкции внутри обычных комментариев не дают полномочий. Первичная привязка разрешает ID владельца токена; общий чат и его агенты, действующие через тот же GitHub аккаунт, используют это разрешение. Отдельные аккаунты не получают доступ автоматически.

## Протокол агента

Каждый запрос — новый комментарий в выбранной Issue. Комментарий начинается точным маркером, затем следует JSON:

```text
<!-- metaengine-chat-request:v1 -->
{"schema":"metaengine.github-chat-request.v1","relay_id":"<из Issue>","client_id":"<из Issue>","method":"STATUS","params":{}}
```

| Метод | Параметры | Результат |
| --- | --- | --- |
| STATUS | `{}` | Состояние клиента и канала |
| CAPABILITIES | `{}` | Реализованные действия и Windows computer plane |
| COMMAND_SUBMIT | `action`, `payload` | Приём существующей команды в PostgreSQL, command UUID |
| COMMAND_LOOKUP | `request_id` исходного комментария | Сверка неопределённого приёма без повторной отправки |
| COMMAND_RECEIPT | `command_id` | Терминальный результат того же устройства |
| GOAL_SUBMIT | `objective`, до 480 символов | Существующий атомарный Client V1 приём цели |
| GOAL_PROGRESS / GOAL_PROOF | `request_id` | Прогресс и доказательства существующей цели |
| REVOKE | `{}` | Постоянный отзыв этой привязки |

Для обзора ПК сначала отправляется COMMAND_SUBMIT с `action: COMPUTER_OBSERVE`, например `payload: {action: OBSERVE_WINDOWS}` или `{action: CAPTURE_DESKTOP}`. После завершения команда читается через COMMAND_RECEIPT. Проверенные PNG из каталога Windows executor публикуются только в закреплённый приватный репозиторий; ответ содержит путь, SHA-256 и размер, а локальный `png_path` удаляется из экспортированного результата. Agent может получить изображение через GitHub Contents. Ответ Issue сам по себе не доказывает физическое выполнение: необходимо читать terminal receipt и его effect outcome.

COMPUTER_ACTION требует существующий `agent_id` и все действующие привязки точного окна, процесса, UIA и DB effect intent. Общий рабочий стол сериализуется существующими полосами команд. Для обычного управления предпочтительны семантические действия и UIA. Визуальный клик сохраняет предел свежести кадра 3 секунды; медленная доставка через GitHub не продлевает его. Произвольный shell/eval не добавлен. CAPTURE_VIEW с большим изображением не получает нового обхода ограничения размера receipt; снимок клиента доступен через захват его окна или рабочего стола.

## Выполнение и восстановление

Путь команды: GitHub Issue → установленный relay → device-signed локальный `/v1/commands/issue-chat` → существующий issue RPC PostgreSQL → существующая lease/effect/receipt обработка Native Supervisor. Сам relay не вызывает Windows executor и не выдаёт себе lease. Lookup фильтруется по аутентифицированному устройству и стабильному idempotency key. Hosted режим отвергает новые маршруты. Миграции базы, новый task store и второй scheduler не добавлены.

ID запроса детерминирован из ID репозитория, Issue, relay, клиента и комментария. Отредактированные команды отвергаются. Перед приёмом на диск эксклюзивно записывается и flush-ится delivery claim. Сохранённый outcome позволяет повторно доставить ответ без нового приёма команды. Claim без outcome после перезапуска даёт AMBIGUOUS_NO_RETRY и требует lookup/progress. Этот журнал относится к доставке, PostgreSQL остаётся владельцем задач и результатов. Проверено восстановление процесса; устойчивость к потере питания не квалифицирована.

Создание Issue также предваряется постоянным claim. Потерянный ответ после возможного создания не приводит к автоматическому повторению. Частичные файлы сохраняются для независимой сверки. Обычная перепривязка отозванного канала через интерфейс архивирует старую привязку и зашифрованный токен, затем создаёт новый relay UUID; старые команды не получают новый grant.

Отзыв из интерфейса работает без доступного GitHub. Отзыв в inbox обрабатывается раньше обычных непрочитанных команд. Перед началом каждой команды с `issued_by: github-chat:...` клиент повторно проверяет grant, срок, файлы и разрешённого оператора. Отзыв, изменение или удаление файлов блокирует ожидающие команды. При ответе GitHub 401/403/404 канал останавливается; это обнаруживается ближайшим опросом. Уже начатый OS effect нельзя гарантированно отменить. Уже принятые автономные цели сохраняют обычный PostgreSQL lifecycle и не отменяются отзывом доставки.

Опрос проводится каждые 5 секунд. Это канал команд и результатов, а не поток удалённого видео. Приватность и ID репозитория перепроверяются перед публикацией. Бесконечная история не замалчивается: при насыщении 16 страниц по 100 комментариев канал останавливается с INBOX_ROTATION_REQUIRED. Повторная привязка выполняется локальной кнопкой. Снимки в приватном репозитории автоматически не удаляются.

## Проверки этого кандидата

- 35 новых тестов (33 для управления и 2 для Windows-compatible source gate): приём через существующий issuer, Computer RPC, device signature, повторная доставка, process restart, неполный claim, потеря ответа, неверный пользователь/Issue/relay/client, public repository, edited comment, scope, expiry, revoke, поздняя публикация, экспорт PNG, защищённые файлы, локальная привязка, отсутствие автоматического повторения Issue creation и перепривязка.
- Вместе с существующими typed bridge и workflow guard тестами: 49 PASS, 0 FAIL, 0 SKIP; дополнительно 24 PASS для startup/singleton и короткого source-check runner.
- Расширенные Browser control regressions (включая новые проверки): 241 PASS, 0 FAIL, 2 Windows-specific SKIP; с дополнительными startup/source-check проверками — 265 PASS.
- Client State Runtime: 149 PASS, 0 FAIL, 4 Windows-specific SKIP в Linux.
- Browser syntax check, полный UI TypeScript check и ESLint изменённого System page прошли. UI проверялся после чистой npm установки; frozen Bun install и production UI build остаются отдельными CI-проверками.
- Полный локальный Browser прогон прерван после ошибок sandbox IPC; его завершение и зелёный результат не заявляются. Эта среда запрещает Unix sockets (`listen EPERM`), поэтому локальные IPC/fixture проверки здесь не могут служить зелёной квалификацией всего Browser. Полный CI и Windows Package Smoke должны проверять точный опубликованный head; результаты предшествующего пакета не переиспользуются.

Первый CI head `7981d3702189a01ec0f91fbf3aa3e3c862500754` обнаружил Windows cmd.exe command length overflow и отсутствие BrowserWindow/ipcMain в унаследованной Electron test fixture. Исправлены проверяющий entrypoint и fixture; production admission gates не изменены. Версия .11 потреблена, исправленный источник использует .12. Отдельный R83 gate сравнивает источник с прежним deployed v14 canary и отвергает drift; этот pin не переписан и квалификация облачного canary не заявляется.

Следующая физическая квалификация: запуск точного нового пакета на Windows с постоянным восстановленным PG17 и оригинальным Vault, привязка отдельного приватного inbox, настоящий запрос из чата, чтение Windows UIA/PNG, подтверждённый эффект на обычном окне, два агента на общем desktop, cold restart и отзыв с ожидающей командой. Наличие исходников или успешных fixture тестов не заменяет эту проверку.
