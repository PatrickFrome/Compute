## 1. Что доказали живые пробы этого раунда

| Проба | Результат | Следствие |
|---|---|---|
| `sb_publishable_…` → таблица зеркала | **PGRST205** (не «Invalid API key») | публичный ключ ПРИНЯТ гейтом; таблицы нет (WARMUP) |
| точная строка legacy **anon** JWT (операторская) | **PGRST205** | зарегистрированный anon принят — загадка A1 снята (наш минт отличался байтом, не секрет) |

| вход GoTrue (password) → REST с access_token | **PGRST205** | НАСТОЯЩИЙ GoTrue-токен гейт принимает! Сам-минт (G1-G3) фейлился из-за неполных claims (нет `aal/amr/session_id`) |

**Главный вывод**: authenticated-RLS-канал из UI осуществим по каноническому пути GoTrue — daemon держит
пароль сервис-аккаунта в vault'е, входит, отдаёт UI короткоживущий токен (exp−iat = 3600с у реального),
рефетчит по истечении. Это и есть изначальный дизайн «mint ttl 120с», только честный: токены выпускает
GoTrue, а не мы.

## 2. Аналоги: «публичный ключ у клиента, секрет у хоста»

- **Electron security model (док. electronjs.org)**: `contextIsolation: true` + `nodeIntegration: false` —
  рендерер принципиально не имеет доступа к Node/секретам; всё привилегированное — через preload-мост
  (`contextBridge.exposeInMainWorld`) с узким API. VS Code строит весь workbench именно так: renderer = UI,
  main/shared-process = секреты и файловая система.
- **VS Code → Settings Sync / telemetry**: клиентские ключи — только публичные идентификаторы; токены
  аутентификации (GitHub/Microsoft) живут в `keytar`/safeStorage main-процесса и никогда не попадают в
  webview-код. Ровно наша пара: «UI держит publishable/anon; service_role — только в daemon».
- **Cursor**: форк VS Code — авторизация AI через собственный бэкенд-прокси; клиент не держит ключей моделей,
  запросы подписываются на сервере. Урок: даже «свой» ключ лучше проксировать, если токен даёт write.
- **Supabase docs (новая модель ключей)**: publishable — «safe to use in a browser», secret — только сервер.
  RLS — единственная граница. Мы теперь соответствуем канону дословно.
- **Firebase**: `apiKey` публичен-по-дизайну (идентификатор, не секрет) — тот же паттерн «публичный
  идентификатор + правила безопасности (rules) как настоящий гейт». Supabase publishable ≈ Firebase apiKey,
  RLS ≈ rules.

## 3. Модель чтения зеркала, принятая в R55 (гибрид)

Данные — через daemon (`/sqlmirror/feed`, service-канал: UI видит события уже сейчас и после DDL);
RLS-гейт — живой пробой облака публичным токеном из UI (anon → обязан видеть 0 строк после DDL —
fail-closed sql/0003). Это соответствует VS Code-паттерну «в webview — агрегат от хоста; в облаке —
правила; прямые клиентские запросы — только публичным ключом».

R56 (созрело): канал `gotrue` в uiTokenBundle — daemon входит сервис-аккаунтом (креденшалы в vault:
`SUPABASE_UI_ACCOUNT_EMAIL/PASSWORD`), кэширует access_token (TTL 3600с), отдаёт в UI; panel пробует
authenticated-чтение напрямую (после DDL увидит строки ПОЛИТИКОЙ authenticated, не обходя RLS);
feed остаётся фолбэком.

  daemon-прокси с честной маркировкой.
