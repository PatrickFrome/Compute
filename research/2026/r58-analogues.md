# R58 — Ресёрч аналогов: «Политики как данные» + двухслойная матрица аудита

Раунд: R58 (2026-09-23) · Источники: живые пробы облака R52–R58 (PostgREST + psql-каталог),
база знаний. web_search: 429 (8-я сессия подряд) — НЕ амплифицирован, одна честная проба.

## 1. «Политики как данные» — канонический узор

Идея: ожидаемое состояние безопасности (гранты/политики/RLS-флаги) — это ДАННЫЕ с
единственным источником (sql/0003+0004), а не память оператора и не «как-то применили».
Аудит = детерминированная сверка факт↔план. Аналоги в индустрии:

| Аналог | Механика | Что взято |
|---|---|---|
| `git fsck` | сверка объектной базы против инвариантов | аудит сам находит свои баги (см. §3) |
| Terraform drift detection | план → live → diff, честный статус | вердикт PASS/FAIL по несоответствию |
| `pg_dump --schema-only` diff | срез каталога против эталона | psql-интроспекция `information_schema`/`pg_policies`/`pg_class` |
| AWS Config rules | «expected state as data» + постоянная проверка | кэш 60с, read-only, вне шины |
| Supabase Studio → Database → Policies | показывает политики списком | НО не сверяет с эталоном и не показывает гранты — наш аудит дополняет Studio |

## 2. Двухслойная матрица: DML строго, платформенные дефолты — info

Живая проба R58 поймала важный факт: кроме наших грантов sql/0004, каталог содержит
**платформенные дефолты Supabase** — `ALTER DEFAULT PRIVILEGES` проекта даёт
REFERENCES,TRIGGER,TRUNCATE всем ролям (включая anon) на каждой таблице.

Разбор (честный):
- REFERENCES/TRIGGER/TRUNCATE — НЕ DML; PostgREST их не открывает (API = SELECT/INSERT/
  UPDATE/DELETE). Угроза через гейт отсутствует; это базлайн любого Supabase-проекта.
- DML-слой — ровно то, чем оперирует гейт: строгое сравнение с sql/0004. anon DML = 0 →
  fail-closed подтверждён данными каталога (и живой 42501-пробой R56 — два независимых
  доказательства одного факта).
- Вердикт аудита = FAIL только при расхождении DML/политик/RLS-флагов; платформенный слой
  печатается info-строкой (без alarm fatigue — урок шумных сканеров, которые «всё красное»
  и потому игнорируются).

Урок для последующих миграций: если когда-нибудь захотим затянуть платформенный слой —
это отдельная sql/0005 (REVOKE TRUNCATE … FROM anon) с re-аудитом; сейчас НЕ делаем
(минимальный DDL-риск > косметика против платформенных дефолтов).

## 3. «Аудит ловит сам себя» — три бага до eval

1. `ORDER BY 1,2` при ОДНОМ выражении select-list → `ERROR: ORDER BY position 2 is not in
   select list` (привычка от запросов с двумя колонками). Фикс: сортировка в bash (norm).
2. Двухслойная семантика: наивный byte-diff давал вечный FAIL из-за платформенных дефолтов.
3. **src/rls-audit.ts: `rmSync(outDir)` до `readFileSync(outFile)`** — результат удалялся до
   чтения, эндпоинт всегда возвращал `no_json`. Изолированный тест спавна это НЕ ловил
   (не шёл через модуль). Поймано живым вызовом эндпоинта, не гейтом — урок: тестировать
   нужно весь путь (endpoint), а не только слой.
