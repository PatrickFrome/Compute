## 1. Read-model зеркало событий + RLS-гейт (наш sqlmirror + панель «Зеркало SQL»)

**Эталоны:**
- **CQRS-проекция (EventStoreDB → SQL read-model)**: журнал событий — истина; SQL-таблица —
  производная read-модель с собственными индексами (у нас: ts desc / type / subject —
  sql/0001 ровно этот паттерн). Идемпотентность по PK (у нас seq) = «at-least-once +
  ignore-duplicates» — стандарт проекций.
- **GitLab/GitHub audit-log stream**: аудит шлётся наружу, но read-модель для UI —
  отдельная поверхность с правами. У нас: RLS = авторизация на уровне строк,
  сервис-роль пишет, read-канал UI — только через политики.
- **Supabase RLS как канонический authz**: политика на SELECT `to authenticated` —
  роль-ориентированный гейт; отсутствие anon-политики = fail-closed. Наша anon-проба
  в UI (ожидаем пусто/401, предупреждение при протечке) — редко встречаемый, но
  правильный «гейт-доказательный» приём: UI не просто читает, он ДЕМОНСТРИРУЕТ, что гейт работает.
- **Chrome enterprise policies / VS Code restricted modes**: read-only поверхности,
  которые честно сообщают «доступ ограничен» вместо тихой пустоты — наш UI делает
  то же (401/404/нет канала — каждая причина словами).

**Новое в R53 (из живой пробы):** режим API-ключей Supabase эволюционировал
(sb_publishable_/sb_secret_ вместо JWT-ключей; HS256-mint отвергается). Вывод —
read-канал должен быть **двухрежимным с честным приоритетом**: publishable (канонический
RLS-гейт нового режима) → mint (если оператор включит legacy JWT) → честный отказ.
Аналог у VS Code: UpdateService пережил смену каналов доставки, сохранив контракт.

## 2. Фаза E: архивация веток (tag-before-delete)

**Эталоны:**
- **Chromium branch cutting**: ветки переходят в refs/branch-heads, мёртвые — чистятся,
  но все точки истории достижимы через теги. Наш паттерн: `archive-2026-09-<ветка>` тег
  → удаление ветки = тот же инвариант «ничего не теряется».
- **VS Code release branches (release/1.8x) + npm dist-tags**: длинно живущие ветки —
  исключение, а не правило; рабочие — срезаются по milestone. У нас: 14-дневное окно
  = аналог milestone-среза.
- **Git-практика «tag before delete»**: стандарт индустрии для retired-веток;
  восстановление = `git branch <имя> <тег>`. Мы добавили манифест-JSON (машиночитаемый
  аудит решений) — аналог changelog-дисциплины.
- **Открытые PR как фенс**: ветки с открытыми PR не трогаются — аналог правил
  GitHub по protected heads. У нас 581 ветка осталась именно из-за открытых PR
  (древний цикл) — отдельное решение оператора (закрыть PR → следующее окно архивации).

**Цифры R53:** 1168 голов → кандидатов по префиксам 1118 → архивировано **292**
(тег+удаление, 0 ошибок, 105с), осталось: 581 открытые-PR + 245 свежих (<14д).
Полное «1025+» закрывается за 2-3 окна по мере старения/закрытия PR.

## 3. Ключевые режимы Supabase и дисциплина инвентаря (K7 продолжение)

- Легаси JWT-ключи (anon/authenticated/service_role, HS256 по JWT-секрету) →
  новые `sb_publishable_…`/`sb_secret_…` (роль anon/service на стороне gateway).
- Урок: **имя секрета ≠ его формат** — vault-запись `SUPABASE_SERVICE_ROLE_JWT`
  содержала sb_secret. Инвентарь ключей должен проверять формат (проба живого
  канала), а не доверять имени. Наш ответ: двухрежимный ui-token + honest 401-текст
  в UI + vault остаётся единственной истиной (значения не тронуты).
- Аналог: миграции VS Code с токенов VS Marketplaces на единый галерейный сервис —
  контракты выживают, транспорт меняется.

## 4. Самоприменение миграций при «ждущем» креденшале

- **Flyway/Liquibase**: миграции — версиируемые артефакты кода (у нас sql/0001..0003
  в репо), применение — отдельная операция с чётким журналом.
- **External Secrets Operator (K8s)**: система ожидает появления секрета и активирует
  контур сама, без человека. Наш `apply-sql-migrations.sh` в start.sh — тот же паттерн:
  как только `SUPABASE_DB_URL` появляется в env-файле, миграции применяются при
  ближайшем старте (идемпотентно), зеркало переходит WARMUP→LIVE само.
- **PGRST205-протокол** (наш, с R50): DDL — только через psql-канал; daemon не
  штормит пробами (≤1/10 мин) — совпадает с backoff-дисциплиной etcd-клиентов.

## 5. Осознанные НЕ-заимствования

- Не используем SECURITY DEFINER-функции старого цикла как SQL-канал (обход
  operator-gate = нарушение протокола честности системы).
- Не храним sb_publishable в UI-бандле (панель получает канал от daemon'а по требованию —
  точка смены канала остаётся одной).
- Не закрываем открытые PR старого цикла автоматически (решение оператора; фенс честный).
