# R54 — ресёрч по аналогам: идентичность ключа против верификации подписи; читаемые зеркала в UI

Дата: 2026-09-23 · Раунд: R54 · Источники: живые пробы облака (E1-E5, A1-A3, G1-G3), локальные знания об аналогах
(web_search был 429 — честно, без амплификации; всё ниже помечено, откуда взято: «проба» = живой эксперимент R54, «аналог» = знания).

## 1. Главное открытие раунда: «ключ-как-идентичность» vs «ключ-как-подпись»

**Проба (R54)**: gateway Supabase отвергает сам-минт HS256 с тем же секретом и каноническими claims (E1: 401),
но принимает точную строку зарегистрированного service_role JWT (E2/E5: 200). Форма GoTrue (iss=/auth/v1, aud,
sub) — тоже 401 (G1-G3). Значит валидация — **точный матч зарегистрированных строк**, а не HMAC-верификация
произвольных токенов. Следствия:
- «short-lived mint» в облаке не существует в принципе — TTL-токены может выпускать только тот, кто владеет
  реестром (GoTrue), и его токены, вероятно, тоже проходят через отдельный путь.
- Ротация секрета не ротирует «идентичность» — identity держится в паре (строка ключа, реестр проекта).

**Аналоги — где ещё встречается эта модель**:
| Система | Модель | Суть |
|---|---|---|
| AWS SigV4-доступ ключей | identity | секрет не «подписывает что угодно» — пара (AKID, secret) ищется в реестре; без известного AKID подпись не проверяется вообще |
| GitHub App tokens | identity+scope | установка-токены выпускаются реестром App'а; сам-подписанные не работают |
| Firebase legacy database secrets | подпись → миграция в identity | классический урок: старый секрет позволял минт любого токена → Google деградировал это до реестра ключей |
| HashiCorp Vault tokens | identity | токен сам по себе — случайная строка, валидная ТОЛЬКО если внесена в хранилище; «подписи» нет |
| Session-куки крупных SaaS | identity | билборд-урок: валидация по реестру сессий, а не по подписи (отзыв мгновенен) |

**Что мы взяли**: канал чтения зеркала перепроектирован честно — `service_proxy` (daemon читает сам, ключ не
покидает сервер) вместо фиктивного минта; слоты `SUPABASE_ANON_JWT`/`SUPABASE_PUBLISHABLE_KEY` — для
канонического RLS-гейта, когда оператор положит публичный ключ. Панель обязана маркировать, что RLS-демонстрация
в service_proxy НЕ выполняется (словами, не молчанием).

## 2. «De-legation чтения телеметрии» — как аналоги показывают облако в UI

- **VS Code → Telemetry** (аналог): локальный клиент пишет в свой журнал, UI настроек показывает агрегаты
  локально; наружу — отдельный канал с отдельными ключами. Урок: UI никогда не держит write-ключ облака.
- **Grafana → Cloud metadata API** (аналог): UI говорит с собственным backend-прокси, а не с облаком напрямую —
  ключи живут на сервере, UI получает уже агрегат. Это ровно наш `service_proxy` + `/sqlmirror/feed`.
- **Supabase Studio** (аналог): сама студия ходит через mgmt-API с PAT оператора — «панель с ключом оператора
  на сервере, не в браузере».
- **Курсор/VS Code updates** (аналог, из r50-r53 ресёрчей): манифест обновлений — публичный по дизайну, приватные
  ключи — только в серверной подписи. Разделение «публичный read / приватный write» — то же, что anon vs service_role.

**Новое для нас**: правило «UI может держать ТОЛЬКО публичный-по-дизайну ключ (anon/publishable); всё
приватное — через daemon-прокси с честной маркировкой отказа от RLS-демонстрации» — записано в код
(contract.ts, supabase-jwt.ts) и в eval v20 (no-leak проверки на eyJ…/sb_secret… в выдаче).

## 4. Осознанные НЕ-заимствования

- **Не делали** brute-force/перебор iat зарегистрированного anon-ключа — это шторм проб против облака
  (нарушает G11/PGRST205-протокол) и нечестно по отношению к реестру ключей.
- **Не ослабляли** eval-инвариант «в HTML нет слова service_role» под новую панель — вместо этого вычистили
  тексты (защита в глубину осталась).
- **Не выдаём** service-ключ в ui-token даже в service_proxy — Grafana-паттерн «агрегат через прокси».

## 5. Что осталось оператору (без чего система честно деградирует)

1. `SUPABASE_DB_URL` (pooler-строка) → система САМА применит sql/0001..0003 при старте (start.sh) → WARMUP→LIVE.
2. `sb_publishable_…` ИЛИ строка legacy anon JWT (лежит в дашборде рядом с тем местом, откуда скопирован
   service_role) → RLS-гейт из UI станет каноническим (каналы publishable/anon_registered уже готовы в коде).
