# Механики автономного клиента: исследование 9 октября 2026

## Результат и границы

Проверены официальные документы Temporal, LangGraph и OpenHands через HTTPS 9 октября 2026 года (дата проекта, Europe/Moscow). Все ссылки в таблице ниже вернули HTTP 200; текст прочитан в Markdown-представлении соответствующих страниц. Это сравнение архитектурных механизмов для METAENGINE, а не рейтинг «лучшей системы 2026». Бенчмарки производительности, самостоятельности и экономической эффективности этих систем не выполнялись. Дата проверки не означает, что каждая механика появилась в 2026 году.

Цель METAENGINE — длительное автономное выполнение задачи с координацией растущего числа агентов и проверяемым улучшением среды. «Неограниченное число» следует реализовывать как отсутствие продуктового лимита на общее количество агентов/задач: активная параллельность каждого узла всё равно ограничена CPU, памятью, пропускной способностью и доступным бюджетом. Бесконечно растущий журнал внутри одного процесса не обеспечивает непрерывность.

## Четыре механики для METAENGINE

### 1. Возобновляемая цель и отдельные попытки внешних действий

Из Temporal применимы стабильный идентификатор цели, отдельный идентификатор попытки и durable history. Перед отправкой агенту или внешнему инструменту записывать намерение с ключом идемпотентности; после выполнения — receipt с идентификатором действия и результатом. При перезапуске сверять receipt и состояние внешней системы перед повтором неоднозначного действия. Новый запуск клиента не должен порождать новую логическую цель или повторно применять уже подтверждённое изменение.

В существующей системе это следует продолжать через штатный Native Supervisor и его command/result path. Ещё один планировщик внутри UI создаст конкурирующего владельца исполнения. UI должен показывать цель, run, попытку, последнее подтверждённое действие и причину ожидания. Проверка приёмки: завершить процесс между внешним эффектом и фиксацией receipt; после восстановления доказать отсутствие повторного эффекта.

### 2. Ограниченная история и управляемое горизонтальное расширение

Из Continue-As-New и LangGraph pending writes применимы последовательные checkpoint epochs и возобновление только незавершённых ветвей. Цель живёт дольше отдельного процесса или контекста агента. Checkpoint содержит необходимое состояние, список выполненных и незавершённых шагов, ссылки на артефакты и последний подтверждённый cursor; полная история остаётся в архиве. Ротация не должна стирать происхождение решений.

Распределять работу между агентами через очередь, lease и backpressure, масштабируя число активных исполнителей по фактической ёмкости. Число зарегистрированных агентов не является числом доказанно работающих исполнителей. Проверка приёмки: тысячи завершений и несколько ротаций checkpoint не увеличивают резидентный UI/event buffer без границ; восстановление пропускает уже завершённые ветви.

### 3. Память выполнения и проверяемые знания между агентами

Из LangGraph применимо разделение thread checkpoint и shared Store. Запись «агент сделал вывод» является наблюдением. Продвижение этого вывода в общую рекомендацию требует происхождения, версии, области применимости и результата проверки. Для улучшений среды сохранять исходную/новую версию, условия оценки и независимое сравнение. Успешная запись в память не доказывает улучшение качества.

Первый практический шаг — связать durable checkpoint цели с версионированными знаниями, не помещая всю общую память в каждый агентный контекст. Проверка приёмки: новая сессия восстанавливает ход задачи из checkpoint и получает только релевантные проверенные знания; отклонённая гипотеза не становится общей инструкцией автоматически. Порог оценки и способ продвижения — проектное предложение METAENGINE, а не утверждение о готовой гарантии LangGraph.

### 4. Изолированное исполнение и достоверный просмотр событий

Из OpenHands применимы самостоятельный execution service/workspace и наблюдающий UI. Перезапуск или пауза интерфейса не должны останавливать исполнение. Agent/tool events образуют журнал, по которому можно понять причину перехода состояния. Текущий heartbeat, готовность coding environment, непрерывность хоста и доказательство полезного результата следует показывать отдельно.

Для обзора большого флота нужен стабильный снимок событий во время расследования: поток продолжает поступать, а выбранное оператором окно сохраняет содержимое и положение прокрутки. Возврат к live — явное действие. Количество новых событий должно иметь честную область: «в текущем буфере», если старые события уже вытеснены. Этот локальный снимок помогает расследованию, но не заменяет durable event archive.

## Реализованный клиентский срез

В `apps/me2-ui/src/components/me2/pages/observability.tsx` найдена воспроизводимая ошибка: при паузе журнал использовал `seq >= frozenSeq`. Для событий `[8, 7]` и новых `[10, 9]` это оставляло `[10, 9, 8]`, то есть показывало будущие события и убирало прежнюю историю. Замена только знака сравнения тоже теряла бы историю после ротации ограниченного transport buffer.

Теперь пауза сохраняет отдельный снимок текущего окна, удерживает его даже при вытеснении live buffer и отключает автопрокрутку. Заголовок явно показывает `paused`; кнопка возврата сообщает количество новых событий, ещё имеющихся в буфере. Пауза пустого журнала остаётся пустой до возобновления. Вспомогательная логика находится в `apps/me2-ui/src/lib/event-log-window.ts`; проверки сценариев — `apps/metaengine-browser/test/client-event-log-window.test.mjs`.

Изменение не добавляет исполнительных полномочий UI и не объявляет автономность достигнутой. Следующий содержательный рубеж всей системы — доказанный цикл «задача → параллельная работа → проверка результата → checkpoint → восстановление после сбоя → продолжение» на реальном клиенте.
