# METAENGINE: целевая модель автономной системы

Зафиксировано по прямому уточнению пользователя 9 октября 2026 года. Это продуктовая цель и критерии разработки, а не утверждение о уже достигнутой готовности.

## Пользовательский контракт

Пользователь задаёт задачу в клиенте. METAENGINE создаёт и поддерживает дерево ChatGPT-агентов: они делят работу, специализируются, общаются, создают дочерних агентов и продолжают выполнение без постоянного участия пользователя. Для задачи самоулучшения объектом работы становятся клиент, среда исполнения, механики координации и конфигурации самих агентов.

Для новой задачи METAENGINE создаёт проект на ПК: устойчивый `project_id`, отдельную рабочую папку, репозиторий там, где он нужен, описание задачи и каталоги артефактов. Проект связывается в БД с исходной целью, деревом агентов, попытками, событиями и версиями. Дочерние агенты получают этот проект либо явно связанную изолированную рабочую копию; одновременные изменения сходятся через проверяемую интеграцию. Существующие пользовательские папки нельзя неявно перезаписывать при создании проекта. После перезапуска открывается тот же проект, а повтор команды создания не создаёт дубликат.

Количество логических агентов и подзадач не имеет фиксированного продуктового потолка. Активная параллельность регулируется фактической ёмкостью ПК/узлов, доступностью ChatGPT и бюджетом. Ожидающие агенты и история хранятся устойчиво; нехватка ресурсов переводит работу в очередь, а не теряет задачу. Внешние ограничения провайдера нельзя убрать обещанием «неограниченно».

Агенты работают через разрешённую пользователем среду ПК и клиента, с одинаковым доступом к необходимым инструментам. Координация эффектов обязательна: одновременные действия в одном окне, файле, ветке или установке требуют владения ресурсом, lease/epoch и проверки результата. Это механизм предотвращения конфликтов между агентами, а не отдельный ручной диалог перед каждым действием. Остановка владельцем должна прекращать новые действия и сохранять незавершённое состояние.

## Общая наблюдаемость и координация

Каждый агент может получить полную разрешённую историю задачи: задания, сообщения, публичные планы и объяснения решений, tool calls, действия, результаты, изменения файлов, проверки, артефакты, ошибки и связи между родительскими и дочерними агентами. Интерфейс показывает тот же журнал с фильтрацией и переходом к конкретному событию.

БД — общий источник событий проекта; UI читает эту историю и отображает общую ленту по проекту, агенту, подзадаче и попытке. Событие содержит монотонный cursor, actor, причинную связь, тип действия, состояние и ссылку на результат. Подписки ускоряют отображение, а чтение по cursor восполняет пропущенные события после reconnect. Агенты используют тот же контракт истории через инструменты чтения/поиска. Событие только в памяти renderer или собственном чате агента не удовлетворяет требованию взаимной видимости.

Скрытая внутренняя цепочка рассуждений ChatGPT недоступна системе. Вместо её имитации агент публикует краткое объяснение решения: цель, наблюдения, допущения, выбранное действие, альтернативы при необходимости и проверяемый результат. Технические ключи и пароли передаются через защищённый механизм доступа, а не общим открытым текстом. «Видеть всё» означает доступ к полной истории через поиск и курсоры, а не помещение бесконечного журнала в каждый ограниченный контекст модели.

Идентичность цели сохраняется при смене процесса, контекста и версии клиента. У каждого агента, подзадачи, попытки и внешнего эффекта есть отдельный ID и причинная связь. Дочерняя задача создаётся идемпотентно с родителем, областью работы и условием завершения. Повтор после сбоя не создаёт дубликат агента или уже выполненного эффекта.

## Обучение и RSI

Специализация агента — это версия его роли, инструментов, контекста и проверенных знаний. Доступ через ChatGPT сам по себе не предоставляет изменение весов базовой модели. Обучение системы реализуется через устойчивую память, проверяемые навыки, изменения среды/инструментов и оценку результатов.

Наблюдение, заявление агента о готовности и независимо проверенный результат — разные состояния. Знание хранит происхождение, область применимости, поколение задачи, использованные версии и доказательство проверки. Ошибка и отклонённая гипотеза остаются доступными как опыт, но не превращаются в подтверждённую рекомендацию. Агент не может самопровозгласить своё изменение улучшением всей системы.

Цикл RSI: обнаружение проблемы → гипотеза → изолированная реализация → build/tests → независимая оценка на заранее определённых сценариях → ограниченный запуск → обновление → наблюдение → продолжение либо откат. Каждая версия связывается с исходным commit, артефактом, проверками и миграцией состояния. Подтверждённая полезная работа не теряется при обновлении, а неясный внешний эффект сначала сверяется, прежде чем выполняться повторно.

## Развитие существующего runtime

Единым контуром исполнения остаётся Native Supervisor с durable task/effect journal. UI наблюдает и управляет им; отдельный конкурирующий scheduler не создаётся. PostgreSQL хранит устойчивую координацию и доказательства. GitHub хранит исходники, review и публично допустимые результаты; приватные данные ПК остаются в предназначенном для них хранилище.

Ближайшие интеграционные этапы:

1. Проверяемое обучение: ранний `RESULT_READY` не считается завершённым и проверенным опытом. Память продвигается только по соответствующему доказательству результата.
2. Исполнение разработки: подключить настоящий verifier backend к Development Plane, который сейчас честно сообщает `prepare_only` и отсутствие execution sandbox. Реально выполнить edit/build/tests и записать receipt; не подменять исполнение флагами readiness.
3. Durable fan-out: связать создание дочерних ChatGPT-агентов, владение задачами, общий журнал и восстановление через существующий Supervisor. Проверить повторный запуск между записью намерения и созданием агента.
4. Восстановление и масштабирование: очередь по ёмкости, проверяемые heartbeat/leases, передача незавершённых ветвей, ротация checkpoint/history и извлечение релевантной памяти.
5. RSI rollout: одна проверенная новая версия среды/клиента, продолжение прежней задачи после обновления и доказанный откат при регрессии.

## Приёмочные сценарии

- Одна пользовательская задача порождает несколько координирующихся ChatGPT-агентов и хотя бы одно следующее поколение дочерних агентов. Их изменения сходятся в проверенный результат, а не только в отчёты об активности.
- Новая задача создаёт проект на ПК и связанное состояние в БД. Повтор команды и рестарт сохраняют его ID/папку; UI и разные агенты видят одинаковые действия и причинные связи, включая события, пропущенные во время отключения.
- Каждый агент и пользователь могут восстановить причинную историю решения по событиям и артефактам, включая отвергнутые гипотезы и проверки.
- Принудительный сбой после внешнего эффекта, но до receipt, не вызывает повторного применения эффекта. Рестарт восстанавливает прежнюю цель и незавершённые ветви.
- Ограничение активной параллельности не теряет подзадачи; увеличение доступной ёмкости возобновляет очередь. Длительная работа не требует бесконечного роста памяти одного процесса.
- Отклонённый critic-ом результат не попадает в verified knowledge. Повторяемое измеримое улучшение может быть принято в shared memory с происхождением и версией.
- Задача «улучшить METAENGINE» проходит один полный RSI цикл с независимой проверкой и рабочим rollback. Новая версия продолжает ту же пользовательскую задачу.
