# METAENGINE: критическая оценка механизмов после разработки 10 октября 2026

Документ сопоставляет [исследование автономных систем](metaengine-autonomy-2026-10-10.md) с текущими исходниками `client-work`. Это состояние рабочей копии, включая изменения нынешней сессии. Наличие реализации, успешная fixture-проверка, собранный пакет и работа установленного клиента — разные уровни доказательства. Ни один из них сам по себе не доказывает улучшение качества автономной разработки.

## Что изменилось в рабочем цикле

Принятая пользовательская цель теперь получает идемпотентную регистрацию проекта по исходному `request_id`. Локальный goal journal сохраняет `project_id` и точную связь с root task. Потеря ответа регистрации и сбой перед сохранением локальной связи восстанавливаются повтором той же регистрации; исходная цель заново не отправляется. Отказ проектных метаданных не превращает принятую задачу в новую неоднозначную отправку.

PostgreSQL содержит проект, родительские связи задач, ожидающие child proposals и общий журнал. Native Supervisor монтирует дополнительный этап существующего task cycle: `PROJECT_SPAWN` пишет намерение в локальный SQLite и обращается к штатной DB admission; штатные FleetProvisioner и DevOsNativeTaskCycle по-прежнему владеют созданием и отправкой физических ChatGPT-сессий. Инструмент истории читает общий DB contract. Для текущей leased mutation host выводит устойчивый workspace ID и использует уже существующий managed-project executor с проверкой signed authority.

Code page читает проект текущей цели и общую историю. Task Sheet проверяет точную связь по native `task_id`; `selected_task` независим от первых 128 строк task pagination. Если ME2-задача относится к другому контракту и точной связи нет, UI сообщает отсутствие привязки. Совпадение заголовков, порядка строк или приблизительного времени не создаёт связи между двумя задачами.

## Критика архитектурного выбора

Решение расширять существующий Supervisor оправдано конкретными границами владения: DB допускает task, supervisor держит lease, managed host применяет workspace effect, renderer читает sanitised projection. Подключение Temporal, LangGraph или другого orchestration SDK не заменит provider-specific message readback, Git integration policy и physical isolation. Их следует рассматривать после измерения нынешних recovery gaps; добавление второй очереди до этого усложнит согласование состояний.

Слабое место текущего проекта — разрыв между доказанной координацией и полезной сквозной работой. Child admission и parent-child tree реализованы, но deterministic provider не создаёт реальные ChatGPT-сессии. Проверка verifier на настоящем process fixture выполняет команды, но не доказывает production sandbox. Собранный UI читает правильный контракт, но сам по себе не доказывает, что установленный runtime применил новые миграции и продолжает прежнюю цель после обновления. Эти различия должны сохраняться в статусах и публичных формулировках.

Другой разрыв — общая история и операционная память. Commit-ordered журнал позволяет восстановить публичную причинность и не терять события после reconnect. Он не выбирает релевантные знания, не оценивает новую рекомендацию и не отменяет ошибочную версию. Promoting unverified events into shared memory создало бы накопление ошибок. Следующий memory contract должен ссылаться на независимый evidence receipt и иметь scope/revision/revocation; отклонённые гипотезы сохраняются как наблюдения.

Пределы текущих DB policy и journals нужны для bounded исполнения, но ещё не реализуют длительную задачу с неограниченным числом логических потомков. Продолжение через epochs должно сохранять общую goal/project identity, завершённые ветви и артефакты, освобождая active memory; новая epoch не разрешает автоматически replay старых внешних effects. Требуется тест, где лимит очереди временно достигнут, затем ресурс освобождается, pending proposal допускается, задача переживает crash и исходный effect не повторяется.

## Ближайшая приёмка

1. На установленном Windows-клиенте принять новую цель, подтвердить project/task IDs в БД, создать рабочую папку и повторно открыть её после перезапуска. Проверить принятую цель без повторной отправки и проектные метаданные после потери ответа.
2. Выполнить один полезный root→child→grandchild сценарий через реальные provider sessions. Ветви производят артефакты; интегратор разрешает shared-file conflict и получает independently verified итог. Admission, generating indicator и отчёт агента сами по себе не засчитываются.
3. Ввести process loss после physical effect до receipt и проверить provider/worktree/update readback. Неизвестная conversation turn остаётся удержанной до разрешения неоднозначности, а подтверждённый effect повторно не применяется.
4. На том же task corpus измерить single agent и bounded recursive strategy с одинаковыми model/budget/harness. Сравнить evidence-qualified success, latency/cost, duplicate effects, missing events, integration failures и rollback regressions.
5. После baseline внедрять history epochs и evaluated shared memory; провести один ограниченный RSI rollout с продолжением исходной цели и рабочим rollback.
